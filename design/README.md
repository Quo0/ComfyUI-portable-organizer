# Дизайн

Палитра, метрики и образцы компонентов. Отсюда цвета попадают в приложение, а не сочиняются заново при реализации — иначе дизайн и код разойдутся на второй неделе.

## Файлы

| Файл | Что это |
|---|---|
| `tokens/tokens.css` | **Источник правды.** Правится только он |
| `build.mjs` | Собирает `dist/` и `preview.html` из исходников |
| `check.mjs` | Проверки палитры: полнота тёмной темы, контраст, неиспользуемые токены |
| `lib/tokens.mjs` | Разбор токенов и расчёт контраста, общий код для сборки и проверок |
| `styles/app.css` | Общий стилевой файл обеих страниц. Компоненты живут здесь |
| `preview.src.html` | Шаблон библиотеки компонентов |
| `screens.src.html` | Шаблон экранов по сценариям |
| `preview.html`, `screens.html` | Собранные страницы. Открываются двойным кликом |
| `dist/tokens.css` | Рабочий файл приложения: палитра и метрики, все три состояния темы |
| `dist/components.css` | Рабочий файл приложения: компоненты без обрамления страниц просмотра |
| `dist/artifact.html`, `dist/screens.html` | Те же страницы без обёртки документа — для публикации |

Собранные файлы не редактируются руками: следующая сборка их перезапишет.

## Команды

```
node design/build.mjs   # собрать dist/ и preview.html
node design/check.mjs   # проверить палитру, падает с кодом 1 при нарушении
```

Проверять полагается до публикации: ошибки палитры невидимы глазом ровно в той теме, которую не смотришь.

## Как устроены токены

Исходник объявляет две темы обычными классами `.theme-light` и `.theme-dark` — так файл остаётся валидным CSS и подсвечивается в редакторе. Селекторы переписываются при сборке, потому что нужны в двух разных видах.

**Для приложения** — `dist/tokens.css`, три состояния темы:

```css
:root { /* светлая — база */ }
@media (prefers-color-scheme: dark) {
  :root:not([data-theme="light"]) { /* системная тёмная */ }
}
:root[data-theme="dark"] { /* явно выбранная тёмная */ }
```

Тёмные объявления повторяются дважды: медиа-запрос нельзя объединить с обычным селектором в один блок. Повтор генерируется из одного определения, руками его писать нельзя — разойдётся.

**Для страницы просмотра** — те же объявления, но на `.t-light` и `.t-dark`. На `:root` они не попадают намеренно: иначе обрамление страницы окрасилось бы светлой темой приложения независимо от темы зрителя, и тёмная панель на тёмном фоне слилась бы.

## Правила

- **Каждый токен светлой темы обязан существовать в тёмной.** Пропуск оставляет цвет неопределённым ровно в одном из трёх состояний темы, и на светлой это не видно. Проверяется автоматически.
- **Ни один цвет не пишется literal-значением в разметке.** Только `var(--token)`. Проверяется автоматически: объявленный, но не использованный токен — сигнал, что палитра разошлась с макетом.
- **Акценты инстансов держатся в узкой полосе яркости**, где цвет проходит 3:1 и на светлом основании, и на тёмном. Пользователь выбирает цвет сам, и предлагать заведомо нечитаемый нельзя.
- **Нейтраль тёплая и очень тихая** — тон около 45°, насыщенность 3–6%. Она обязана быть тише восьми пользовательских акцентов, иначе подкрашивает их.

## Куда это едет дальше

В Фазе 0.5 в `apps/desktop/src/styles/` переезжают оба собранных файла: `tokens.css` и `components.css`. Компоненты Vue берут цвета только оттуда.

**Оба подключаются глобально, один раз.** `<style scoped>` в SFC остаётся только для раскладки конкретных экранов. Это выбор против привычного «каждому компоненту свой scoped-блок»: разрезав библиотеку по SFC, мы получили бы расхождение с `design/` при первой же правке, а весь смысл каталога в том, что приложение и образцы делят один источник.

Измерено на текущей версии: из 215 правил в приложение едут 164, остальные — обрамление страниц просмотра. Классов компонентов 104, все предметные, ни одного общеупотребительного вроде `.row-2` или `.mt-4`, поэтому глобальная область не мешает.

Селекторов, пересекающих границы будущих компонентов Vue, **ноль** — проверено разбором. Это значит, что `:deep()` при переносе не понадобится нигде.

## Примитивы

Мелкие сущности, не принадлежащие ни одному компоненту, вынесены в отдельный слой. Пока там один `.chip` — цветная метка инстанса, которая встречается и в навигации, и в списке совместимости. Без этого слоя появился бы селектор `.compat-row .chip`, пересекающий границу компонента.

Акцентный цвет приходит в компоненты **через переменную**, а не выбирается из палитры на месте: `.chip` и `.card-accent` читают `var(--instance-accent)`, а разметка задаёт её на элементе. В приложении цвет выбирает пользователь, так что макеты сразу показывают тот же способ связывания, что будет в коде.

## Состояние

Дизайн доведён до конца в три итерации.

**Библиотека компонентов** (`preview.html`) — одиннадцать разделов: палитра, типографика, рейл навигации, карточка инстанса, действия, поля ввода, уведомления и прогресс, пустой реестр, шаги мастера, категории моделей, совместимость воркфлоу. Каждый в обеих темах.

**Экраны** (`screens.html`) — двенадцать экранов, покрывающих все шесть сквозных сценариев из `specs/journeys.md`. Собраны из компонентов библиотеки, а не нарисованы заново: стилевой файл у обеих страниц один, поэтому правка компонента меняет его и на экранах.

Не показаны экраны исключительных ситуаций: разрешение конфликта с чужим `extra_model_paths.yaml` и отчёт о дубликатах моделей — оба относятся к поздним фазам.

## Пары «светлая / тёмная»

Содержимое панели пишется **один раз** внутри `<template>`, обе темы разворачиваются при сборке:

```html
<div class="pair" data-pair="Светлая|Тёмная">
  <template>…содержимое…</template>
</div>
```

Дублировать пару руками запрещено и проверяется автоматически: тринадцать пар со временем разойдутся по содержимому, и сравнивать темы станет не с чем.

Таблица ролей палитры и сетка акцентов генерируются прямо из токенов — подписанный hex не может разойтись с реальным цветом.
